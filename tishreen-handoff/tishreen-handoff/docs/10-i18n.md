# 10 — Internationalisation (ar default · en secondary)

## 1. Principles
1. **No literal UI text in components.** Every string is `t('key')`. Hook `check-frontend-rules` flags Arabic letters or quoted English sentences inside JSX.
2. `ar.json` is complete; `en.json` may lag — i18next `fallbackLng: 'ar'`.
3. Database content is bilingual by columns; the **service layer** resolves `name = name_en ?? name_ar` per `Accept-Language`. Components never do `?? nameAr`.
4. Direction follows language: `ar → dir="rtl"`, `en → dir="ltr"`, set on `<html>` in `__root.tsx`; persisted in `localStorage('tishreen.lang')` and `users.preferred_language` when logged in (`PATCH /me`).

## 3. Formatting helpers (`src/lib/i18n/format.ts`)
- `formatMoney(amount: string, lang)` → `Intl.NumberFormat(lang === 'ar' ? 'ar-SY-u-nu-latn' : 'en', { maximumFractionDigits: 0 })` + currency label from `common.currency`. Western digits by default (`nu-latn`); a future setting may switch to `nu-arab`.
- `formatQty(qty, unit, lang)` → `1.250 كغ` / `2 قطع`.
- `formatDate(iso, lang)` → `Intl.DateTimeFormat` with `timeZone: 'Asia/Damascus'`.
- `formatRelative(iso)` for queue ages ("منذ 4 دقائق").

## 4. Backend messages
`messages_ar.properties` (default) / `messages_en.properties`: keys = error codes (`ORDER_INVALID_TRANSITION=لا يمكن …`) and notification templates (`order.update.CONFIRMED=استلمنا طلبك #{0} وسنبدأ تحضيره`, `otp.activation=مرحبًا {0}، كود تفعيل حسابك…`). `LocaleResolver` reads `Accept-Language`; notifications use the **recipient's** language (`users.preferred_language` / `orders.lang`), not the caller's.

## 5. Slugs
Latin, lowercase, hyphens; generated from `name_en` when present else transliterated from `name_ar` (simple map) with numeric suffix on conflict; always editable by admin; immutable once a product has orders (redirect table not needed at this scale — keep old slug).

## 6. Checklist per screen
- [ ] All strings via `t()`; keys exist in `ar.json`.
- [ ] Renders in `dir=rtl` and `dir=ltr` without overflow.
- [ ] Numbers/phones isolated with `<bdi>`/`dir="ltr"`.
- [ ] Dates/money through the helpers.
- [ ] Error codes covered in `errors.*`.

## 7. React Native (`apps/mobile` — ADR-0004, spec `14-mobile.md`)

Same principles, same key naming (§2), same plural rules — these RN specifics apply on top:

1. **Resources**: `apps/mobile/src/i18n/ar.json` / `en.json` follow §2 verbatim. Keys for concepts that exist on both platforms (`nav.*`, `product.*`, `checkout.*`, `order.status.*`, `errors.*`, `common.*`) are **copied from the web files**, never re-invented — same key, same Arabic string. Mobile-only screens add keys under their own area (`search.*`, `appUpdate.*`).
2. **Locale**: `expo-localization` supplies the device locale, but the app still defaults to `ar` (`fallbackLng: 'ar'`); the choice persists in AsyncStorage (`tishreen.lang`) and, when logged in, via `PATCH /me` (`users.preferred_language`) — the same two stores as web.
3. **Direction**: RN has no `dir` attribute — layout direction is process-wide via `I18nManager`. Bootstrap in the root layout: `I18nManager.allowRTL(true)`; when the stored language's direction differs from `I18nManager.isRTL`, call `forceRTL(…)` and prompt for an **app reload** (`expo-updates` `reloadAsync()`; the module is used **only** for reloading — OTA updates stay disabled: `updates.enabled: false`, no `updates.url` in `app.json`, because EAS Update is a US-hosted runtime service, `11`; verified in the release protocol `14-mobile.md §8`) — a direction change never applies half-rendered. Styles use only logical properties/values (`marginStart/End`, `paddingStart/End`, `start/end`; `textAlign: 'left'|'right'` is forbidden — use `'auto'`/`'center'`); flexbox rows follow `I18nManager` automatically, never reverse arrays manually (same rule as `08 §4`).
4. **Hermes & `Intl`**: Hermes on Android ships `Intl.NumberFormat`/`Intl.DateTimeFormat`, so the money/qty/date helpers (`10 §3`) port 1:1 to `apps/mobile/src/lib/i18n/format.ts` — `ar-SY-u-nu-latn`, Western digits, `Asia/Damascus`. Hermes does **not** ship `Intl.PluralRules` (i18next needs it to pick the Arabic plural suffixes) — bundle the `intl-pluralrules` polyfill and import it before i18n init, or Arabic counts silently collapse to `_other`. `Intl.RelativeTimeFormat` is also missing — `formatRelative` is staff-only and not needed on mobile; if it ever is, implement it with i18next plural keys, not the Intl API. M-T2 (`12`) verifies the three helpers + a plural key on a real device; if a device lacks ICU data, the fallback is a bundled minimal formatter (thousands separator + `common.currency` label), never silent wrong output.
5. **Bidi isolation**: numbers, phones, order numbers and OTP codes inside Arabic text are wrapped with the Unicode isolates `⁦…⁩` (LRI…PDI) via a shared `<Isolated>` text helper (RN has no `<bdi>`, and the `writingDirection` style is **iOS-only** — never rely on it for Android). Inputs: the OTP input is one box per digit with `textAlign: 'center'` (direction-neutral, no bidi problem); the phone input keeps the `+963…` mask LTR via an LRM (`‎`) prefix on the displayed value.
6. **No literal UI text** — identical to web rule 1; enforced by review + the static checks in `13 §5`, because the `check-frontend-rules` hook watches only the web workspaces (`apps/web`, `packages/ui`), not `apps/mobile`.
